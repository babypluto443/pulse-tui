## 一、这一阶段做了什么（一句话版）

把真实网络 IO 接上了：P1 的"心脏"（控速器）通过 channel 把号交给 N 个工人，工人发 HTTP 请求、记录原始结果；Ctrl-C 一按，发射立即停止、在途请求自然跑完、报告照常出——**发号 → 在途 → 排水 → 报告全链路闭环**。

## 二、grill-me 定案的 4+1 个决策

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 函数式 `Run(ctx, cfg, signals) (<-chan Result, error)` | 与 P1 风格一致；attack 是 Result 唯一生产方，WaitGroup 归零后 close |
| 2 | Result 4 字段原始记录（Timestamp/Latency/StatusCode/Error） | Error 只装传输层失败，2xx/4xx/5xx 分类裁判权归 P3；Result 不当裁判 |
| 3 | **在途自然跑完**：请求挂内部 drain ctx（全部工人完工后才取消） | Ctrl-C 中断在途会让报告末尾多一簇人为错误尖峰，与"前半段数据不浪费"相抵；最坏排水 = -timeout |
| 4 | burst = `-c`，signals channel 由 main 创建 | 排队上界 = 2c；背压响应快；"背压阈值就是工人池大小"好讲好测 |
| 5 | Transport：MaxIdleConnsPerHost=MaxConnsPerHost=c，不启 HTTP/2 | 默认 MaxIdleConnsPerHost=2 在高 RPS 下必抖；连接层上限与工人池对齐 |

## 三、逐文件详解

### 1. `internal/attack/attack.go` —— 攻击器本体

**关键设计 ①：drain ctx 与主 ctx 分离（本阶段最重要的决策落地）**

请求挂 `drainCtx`（Background 派生），**不挂** Ctrl-C 的主 ctx。主 ctx 取消只管"停止取号"；在途请求继续跑完，latency 照常入账。`cancel()` 在 `wg.Wait()` 之后才调用——所有工人收工瞬间解除 drain 资源，兜底防泄漏。这样 `http.NewRequestWithContext` 的"第二条取消通道"依然存在（client.Timeout + drain 收尾），但不会误伤在途数据。

**关键设计 ②：两级 select 实现取消优先（对 P1 契约的履约点）**

```go
select { case <-ctx.Done(): return; default: }   // 第一级：非阻塞优先查
select { case <-ctx.Done(): return; case _, ok := <-signals: ... }  // 第二级：等号
```

没有第一级，Go 的 select 在多个就绪分支里**随机选**——取消瞬间缓冲里还有遗留号，工人可能又执行掉几个，破坏"立即停止发射"。两级写法给 ctx 以绝对优先级。

**基础概念**：
- **`io.Copy(io.Discard, resp.Body)`**：必须把响应 body 读干净，TCP 连接才能归还连接池复用 keep-alive；只 Close 不读完，连接作废，每个请求都重新握手，高 RPS 下 TIME_WAIT 爆炸。
- **`bytes.NewReader(cfg.Body)` 每请求新建**：Reader 有读取游标，复用的话第二个请求的 body 就从上次读完的位置继续——等于发了个空 body。
- **StatusCode=0 表示"没拿到响应"**：0 与任何真实状态码不冲突（真实状态码从 100 起），P3 不需要额外的"有没有响应"标志位。

### 3. `cmd/pulse-tui/main.go` —— 总装

`signal.NotifyContext(os.Interrupt)` → `signals := make(chan struct{}, c)`（burst 决策落地）→ `go rate.Run(...)` → `attack.Run` → `range results` 计 total → 占位报告（total/耗时/粗算 RPS）。rate 的错误在报告后从缓冲 channel 收取，`context.Canceled` 静默（那是 Ctrl-C 的正常结局）。

## 四、本阶段的设计哲学（浓缩版）

1. **取消和排水是两件事**：停止发射（快，毫秒级）≠ 回收在途（慢，由服务端决定）。把它们耦在一个 ctx 里，就会为了快而牺牲数据，或为了数据而牺牲响应性。
2. **select 的随机性是语义炸弹**：多分支就绪时 Go 不保证顺序——需要优先级就必须显式两级 select。
3. **测试替身要避免复刻被测系统的错误**：测试里手写 `time.Sleep(10ms)` 循环发号，把 P1 修掉的漂移 bug 又请了回来——修法是让测试直接用真实现（rate.Run），替身只替"边界外"的东西。

## 五、踩坑记录

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| ① 测试假 rate 漂移 | TestRateAccuracy 实测 92 RPS（期望 100） | 测试替身用相对间隔 `Sleep(10ms)` 循环，200 次迭代累积漂移几十毫秒——正是 P1 修掉的错误做法 | 换真 rate.Run，替身问题归零，还白得一层集成覆盖 |
| ② 超时 Latency=0 | TestResultFields 超时子用例红 | doOne 传输失败路径忘记 latency | 失败请求的耗时也是真实数据，`time.Since(start)` 照记（SPEC §5 口径） |
| ③ Run 双返回值漏写 | 编译错 not enough return values | 从单返回值改 `(<-chan Result, error)` 时漏了一个分支 | — |

**方法论收获**：契约字段"一次定好"的价值在 ② 兑现——latency 的口径写在测试里，实现偷懒当场红。**契约测试就是给未来的自己上的闹钟**。
