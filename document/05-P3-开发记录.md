## 一、这一阶段做了什么（一句话版）

把 Result 流变成了可信数字：热路径聚合（零锁计数 + 定长数组状态码分布）、请求窗口口径的实测 RPS、排序分位数，文本/JSON 双轨渲染同一份快照——**"口径对齐竞品"的承诺落地**。

## 二、grill-me 定案的 4 个决策

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | RPS 用**请求窗口**口径（最后响应完成 − 首请求开始） | 排水尾巴不计入分母；墙钟口径会低估脸面数字 |
| 2 | 混合并发策略：3 atomic + `[1000]atomic.Int64` 数组 + mutex latency 切片 | 定长数组零锁零分片胜过分片 map；append ~50ns 在 10k RPS 下锁占用可忽略——PLAN 的锁竞争预警在此量级是伪问题，数据说话 |
| 3 | JSON 契约 8 字段 + errors 分组，只增不改 | P4 TUI 数据源；键名字段回归测试钉死 |
| 4 | 非 2xx 一律 failed（补 SPEC 的 3xx 真空） | SPEC 白纸黑字"成功=2xx"；压测职责是暴露异常（裸 3xx = 目标行为不符预期） |

## 三、逐文件详解

### 1. `internal/metrics/metrics.go` —— 聚合器

**关键设计 ①：`[1000]atomic.Int64` 定长数组替代状态码 map**

HTTP 状态码只可能落在 0~999（0 = 传输失败无响应），一个 8KB 定长数组把"分片 map / atomic per-code"的复杂度整个消掉：写 = 下标 + atomic Add，读 = 1000 次 Load。PLAN 预警的分片方案是为"任意 key 的 map"设计的，我们的 key 空间天然有界——**先看数据结构有没有界，再决定要不要分片**。

**关键设计 ②：请求窗口的 CAS min/max**

首请求开始 = min(Timestamp − Latency)，末响应完成 = max(Timestamp)。并发下更新极值用 CAS 循环（新值更优才换，失败即被抢先、重读重试）。UnixNano 存 int64，0 作"未设置"哨兵。

**关键设计 ③：Snapshot 是深拷贝**

latency 拷贝后排序（内部切片保持纯 append 语义）、两个 map 全部重建。测试 `TestSnapshotImmutable` 蓄意污染返回值再验内部——**不可变承诺必须用测试钉死**，这是 P4 TUI 拿快照渲染的安全前提。

**基础概念**：分位数口径 `idx = ceil(q*n) - 1` 写进注释 + `TestPercentileFixed` 用已知样本（1ms..10ms → P50=5ms、P90=9ms、P99=10ms）钉死。"差一位"的口径漂移是统计工具最阴的 bug，测试就是闹钟。

### 2. `internal/report/report.go` —— 双轨渲染

- `JSONReport` struct + json tag 就是 P4 的契约本身；`status_codes` 键字符串化（JSON 对象键只能是字符串）
- `Text` 对齐 hey 排版四段式；latency 在**报告层**才转 ms（聚合层永远存 ns 不丢精度，`ms()` 是唯一换算点）
- 两个函数消费同一份 `Snapshot`——一致性是结构保证，不靠对账

### 3. `cmd/pulse-tui/main.go` —— 接线与一个契约修正

聚合循环只有三行（range → Add → Snapshot）。**发现并修掉一个输出契约污染**：`-json` 模式下"参数确认"回显混在 stdout 里，下游 `| jq` 直接炸——参数回显整体挪到 stderr（诊断信息与报告通道分离）。

## 四、本阶段的设计哲学（浓缩版）

1. **双轨一致性靠结构不靠纪律**：让两种渲染函数吃同一份输入，"数字不一致"在物理上不可能发生。
2. **性能优化要有数据辩护**：mutex latency 切片看起来"违反"PLAN 的警告，但 50ns × 10k RPS 的账算得清清楚楚；反过来定长数组优化看似激进，实际是利用了 key 空间有界这一结构事实。
3. **契约的边界不止字段**：stdout/stderr 的分工也是契约——管道消费方默认 stdout 只有承诺过的东西。

## 五、踩坑记录

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| ① 期望值算错 | TestConcurrentAdd 红：Failed=1000 vs"期望"1100 | `%100==0` 同时是 `%10` 的倍数，switch 先命中传输失败分支，500 桶要减重叠 | 重算期望：failed = 100 + 900 = 1000（测试的期望值本身要像被测代码一样被审视） |
| ② 测试替身 data race | -race 报 close+send 竞态 | 替身拆成两个 goroutine：一个 close、一个还在发——真实 rate.Run 从不允许这种情况（发送与 close 同 goroutine 串行） | 替身按被测系统的不变量重写（defer close 在发送循环自己的 goroutine 里） |
| ③ -json 输出被污染 | stdout 开头是"参数确认"文本 | P0 的回显用 fmt.Println 打到 stdout | 回显整体挪 stderr |
| ④ hey 对比参数不对等 | hey 平均延迟 24ms vs 我们 1.35ms | hey 用 50 工人（50 连接）挤爆单线程 python；且其 Transport 未调 MaxIdleConnsPerHost（默认 2）连接频繁重建 | 对等参数 -c 10 -q 10 重比；延迟差反而是我们 P2 调参收益的实证 |

**方法论收获**：`-race` 抓到的是**测试替身**的 race 而非产品代码——race detector 检查的是整个进程，替身也是并发程序。替身越简单越好，最好直接用真实现（P2 的教训又一次应验）。
