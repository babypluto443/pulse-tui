## 一、这一阶段做了什么（一句话版）

造出了项目的"心脏"：一个按恒定 RPS 精确发号、误差不累积的调度函数。它还不接 HTTP（那是 P2 的事），但发射节奏已经达到验收线：rate=100 时 100 个号的相邻间隔几乎全落在 10ms±2ms 内，连 5 轮测试无一偶发红。

## 二、grill-me 定案的 5 个决策（开发前锁定）

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 普通函数 `Run(ctx, cfg, ch)`，不抽接口 | 单实现不配抽象；v2 出现第二种调度策略再长出 Pacer |
| 2 | Deadline 驱动截断 | 只判"预定时刻 ≤ Deadline"，不预计算 total，杜绝两套判定打架 |
| 3 | `OnEmit` 可空回调打点 | 发射时刻的权威定义在调度器侧；nil 时零开销 |
| 4 | Run 唯一 close 责任方，取消返回 `ctx.Err()` | close 责任方唯一，P2 用 range 天然安全 |
| 5 | Timer 睡到绝对时刻 + 分布断言 | 单次硬断言会偶发红；先跑数据再决定要不要忙等 |

## 三、逐文件详解

### 1. `internal/rate/rate.go` —— 控速器本体

**做什么**：一个函数 `Run`，向调用方给的 channel 按恒定节奏发 `struct{}{}` 信号，直到 Deadline 或取消。

**关键设计 ①：绝对时间表（本包的灵魂）**

```go
start := time.Now()
// 循环内：
next := start.Add(time.Duration(float64(n) / cfg.Rate * float64(time.Second)))
```

第 n 个号的预定时刻**只由 start 和 n 决定**，与"上一个号实际何时发出"无关。对比错误做法 `time.Tick(1/rate)` 等间隔发号：每次睡眠的误差会**累加**，压 60s 后实际 RPS 明显偏离目标；绝对时间表下单次误差不累积——本次睡过头 2ms，下一个号的预定时刻不会跟着顺延。

**关键设计 ②：追赶语义**

如果因背压（下游消费慢）落后于时刻表，`wait <= 0`，跳过睡眠立即补发。平均 RPS 仍对齐目标，漂移不累积——这是 SPEC §5"正常降级"的实现基础。

**关键设计 ③：close 责任与 defer 的注册位置（本阶段踩的第一个真坑）**

`defer close(ch)` 必须**注册在所有可能 return 的校验之前**。第一版把参数校验写在 defer 前面，导致"参数错误"路径直接 return、channel 没关，测试端 `<-ch` 永久阻塞——goroutine dump 一眼定位（`goroutine 6 [chan receive]`）。教训：**"任何退出路径都 X"这类承诺，X 的 defer 必须放在函数最前面**（nil channel 除外，无从 close）。

**基础概念**：
- **Timer 复用 vs time.After**：`time.After` 每轮在堆上分配新 Timer，到期前无法 GC；高 RPS 长压测下是纯浪费。所以用单个 `time.NewTimer` + `Reset` 循环。注意 `Reset` 前必须确认旧值已排空（`NewTimer(0)` 立即触发的那一发要 `<-timer.C` 掉）。
- **select 双路监听**：睡眠和发送都用 `select { case <-ctx.Done() ... case ... }`，保证取消在任何阻塞点都能立即生效。

### 2. `internal/rate/rate_test.go` —— 五个测试

| 测试 | 验什么 | 关键点 |
|---|---|---|
| `TestIntervalDistribution` | M1 验收主体：≥90% 间隔 ∈ [8,12]ms + 总耗时 990ms±5% | 分布断言不偶发红 |
| `TestDeadline` | rate=10、deadline=350ms → 恰好 3 个号 | 边界离 50ms，抗抖动 |
| `TestCancel`（2 子场景） | 睡眠中取消 / **背压阻塞中取消**，都返回 `ctx.Err()` 且 channel 已关 | 取消时机 1.5s > 首号发射 1s，才能命中发送阻塞路径 |
| `TestCloseOnNormalEnd` | 返回 nil、range 自然退出、5 个信号一个不少 | — |
| `TestInvalidConfig` | 参数错误 fail-fast 且 channel 仍被 close | 逼出了 defer 位置 bug |

**基础概念**：OnEmit 回调把时刻 append 进切片，测试在 Run 返回后才读——同一 goroutine 顺序执行有 happens-before 保证，**不需要锁**。锁是给真正的并发访问用的，不是"加了总没错"。

### 3. `cmd/ratetest/main.go` —— 人肉验收工具

独立调试命令（自有 `-r/-n` flag，不占主 CLI 契约），逐行打印发射时刻与间隔，结尾输出 min/avg/p50/p95/max。分位数口径用 `ceil(q*n)-1`，**提前与 P3 metrics 对齐**，保持项目内统一。

## 四、本阶段的设计哲学（浓缩版）

1. **承诺与实现要同构**：doc 注释承诺"任何退出路径都 close"，defer 就必须放在所有 return 之前——注释和代码是同一份契约的两半。
2. **deadline 的余量要和节奏同尺度**：余量是"半个发射间隔"而不是拍脑袋的 1s，否则余量本身制造了额外名额（见踩坑②）。
3. **结构性排除死锁优于小心谨慎**：ratetest 加后台排水 goroutine 兜底后，无论参数怎么给都不可能死锁，而不是"参数算对了就没事"。

## 五、踩坑记录（本阶段三个，全靠 goroutine dump / exit code 定位）

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| ① 测试死锁 | `go test` 卡死被杀，exit 137 | Deadline 放宽到 2s → 预定 200 个号，缓冲 100 装不下，测试端又等 Run 返回才消费 → 循环等待 | Deadline 精确取 1005ms（第 100 号可发、第 101 号越线），注释写明缘由 |
| ② ratetest 死锁 | `-r 100 -n 100` crash，fatal error: all goroutines asleep | deadline 余量固定 1s ≫ 发射间隔 10ms，等于多放 100 个名额 | 余量 = 半个间隔（0.5/r，夹在 µs~500ms）+ 后台排水 goroutine 兜底 |
| ③ 错误路径不 close | TestInvalidConfig 卡在 `<-ch` | 参数校验 return 发生在 `defer close` 注册之前 | ch==nil 检查最先，defer close 提到所有校验之前 |

**方法论收获**：`go test -timeout 30s` 让框架自己超时并打印**全部 goroutine 栈**，比外部强杀（exit 137、无输出）有用一百倍——死锁排查第一步永远是让死者开口。
