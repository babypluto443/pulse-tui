# pulse-tui · P3 任务清单（grill-me 细化版）

> 日期：2026-10-09 · 依据 PLAN P3 + SPEC §5，经 grill-me 拷问会定案

## 一、已锁定的设计决策（4 项）

| # | 决策点 | 结论 | 理由摘要 |
|---|---|---|---|
| 1 | 实测 RPS 口径 | **请求窗口**：elapsed = 最后响应完成 − 首请求开始（从 Result 的 Timestamp−Latency / Timestamp 推得） | 排水尾巴不计入分母，RPS 如实反映引擎能力；墙钟口径会把 Ctrl-C 排水算进分母，低估脸面数字 |
| 2 | 热路径并发策略 | 混合：total/success/failed 用 3 个 `atomic.Int64`；状态码分布用 `[1000]atomic.Int64` 定长数组（0=传输失败桶，≥1000 越界进 999 溢出桶）；latency 切片 + errors map 共用一把 mutex | 定长数组比分片 map 更简单且零锁；latency append 均摊 ~50ns，10k RPS 下锁占用可忽略——PLAN 预警的锁竞争在此量级是伪问题，数据说话 |
| 3 | JSON 契约（P4 数据源，只增不改） | `total / success / failed / duration_ms / rps / latency_ms{mean,p50,p90,p99,p999} / status_codes(键为字符串) / errors(传输错误分组)` | status_codes 键必须字符串化（JSON 限制）；errors 分组超 SPEC 最低要求但排障价值大，只增不改兼容 P4 |
| 4 | 3xx 归类（SPEC 真空地带补缺） | **非 2xx 一律 failed**（含 3xx、1xx、0=传输错误） | SPEC 白纸黑字"成功=HTTP 2xx"；压测职责是暴露异常（裸 3xx = 目标行为不符预期）；状态码全量分布保底不丢信息 |

**成败口径定稿**：success = 200≤code≤299；failed = 其余一切（4xx/5xx/3xx/1xx/code=0）。
**分位数口径定稿**：升序取 `v[ceil(q*n)-1]`（与 ratetest 已对齐，全项目唯一口径）。

## 二、任务清单

| 编号 | 任务 | 要点 | 完成标志 |
|---|---|---|---|
| T3.1 | `internal/metrics/metrics.go`：Aggregator | ① `New() *Aggregator` + `Add(r attack.Result)`（热路径：3 atomic + 数组下标 + mutex append）② 首请求开始/末响应完成用 atomic CAS 维护 min/max ③ `Snapshot()` 返回不可变汇总：latency **拷贝后排序**（不动内部切片）、StatusCodes/Errors 转 map 拷贝 | Add 无锁热点，Snapshot 深拷贝 |
