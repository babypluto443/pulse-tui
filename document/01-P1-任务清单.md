## 一、已锁定的设计决策（5 项）

| # | 决策点 | 结论 | 理由摘要 |
|---|---|---|---|
| 1 | 对外 API 形态 | 普通函数 `Run(ctx, cfg Config, ch chan<- struct{}) error` | 单实现不抽接口（YAGNI）；参数收进 Config，加字段不改签名；v2 出现第二种调度策略时再抽 Pacer |
| 2 | `-d` 截断语义 | Deadline 驱动 | 循环只判定"预定时刻 next ≤ Deadline"，不预计算 total，避免浮点取整边界和两套判定不一致 |
| 3 | 发射时刻记录 | channel 载荷 `struct{}`；`Config.OnEmit(n int64, at time.Time)` 可空回调 | 发射时刻的权威定义在调度器侧；回调 nil 时零开销，热路径不为测试买单 |
| 4 | 取消与 close | Run 是唯一 close 责任方；ctx 取消立即 return 并返回 `ctx.Err()`；缓冲遗留号由消费端丢弃 | "立即停止发射"的准确语义；close 责任方唯一，P2 用 range 消费天然安全 |
| 5 | 精度与断言 | `time.Timer` 睡到绝对时刻（第一版不忙等）；断言走整体分布 | 单次硬断言会偶发红；先跑数据，真不达标再按 PLAN 升级"deadline−2ms + 忙等" |

**Config 定稿字段**（不多不少）：
```go
type Config struct {
    Rate     float64     // 每秒发射数，> 0，支持亚赫兹（0.5）
    Deadline time.Time   // 最后一个可发射号的预定时刻上限
    OnEmit   func(n int64, at time.Time) // 可空；调度器侧发射打点
}
```
channel 由**调用方**创建传入，缓冲容量即 burst，背压语义由此产生（P2 定容量）。

## 三、给 P2 立下的契约（提前公告，P2 履约）

- worker 消费 channel 必须在 select 里同时监听 `ctx.Done()`——**不能闷头 range**，否则 Ctrl-C 后会把缓冲遗留号照发不误，破坏"立即停止发射"
- channel 容量（burst）由 attack 层定；容量满时 Run 阻塞 = 背压降级，属正常，实测 RPS 如实反映
- close 责任方是 rate.Run，attack 侧绝不允许 close

## 四、明确不做（防膨胀）

- ❌ 不加 `-n` 双模式（v2 场景能力）
- ❌ 第一版不实现忙等补精（数据说话后再说）
- ❌ 不做 `time.Ticker` 等间隔版做对比实验（错误做法写进注释即可，不写进代码）
